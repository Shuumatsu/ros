# rfs 设计：心智模型

这份文档讲的是**怎么在脑子里想这个文件系统**——概念、为什么这么设计、几个关键的认知跳跃，以及我们**故意不做**的东西。不是代码说明。看完你应该能自己在纸上画出「读一个文件」「建一个文件」摸了哪些块。

数字都以本项目的实际参数为准（块 512B、盘 32MiB 等），附录有一张总表。

---

## 0. 一句话

**把一块「编号块的平坦数组」变成「有名字的文件树」。** 整个文件系统就是干这一件事。剩下的全是细节。

---

## 1. 在文件系统眼里，磁盘是什么

磁盘不是「文件的容器」。在我们这一层，它就是一个**定长块的平坦数组**，只提供两个操作：

```
read_block(n)  → 把第 n 块的 512 字节读出来
write_block(n) → 把 512 字节写到第 n 块
```

- 一块 = 512 字节 = 1 个硬件扇区（1:1，不玩读改写）。
- 32 MiB 的盘 = 65536 块，编号 `0 .. 65535`。
- **磁盘本身没有「文件」「目录」「名字」的概念。** 它只有编号的块和块里的字节。

> 记住这条：**文件系统里所有的「结构」，都是我们自己往这些裸字节里塞的约定。** 磁盘不帮你，硬件也不认识 inode。inode、目录、位图，全是我们对某些块里字节的**解释**。换个文件系统去读同一块盘，看到的就是另一套东西（或者一堆乱码）。

---

## 2. 五个区：元数据 vs 数据

我们把这 65536 块划成五段。**顺序固定，大小由格式化时决定**：

```
块号 →
┌──────────┬──────────────┬─────────────┬──────────────┬─────────────────────────┐
│ super(0) │ inode bitmap │ data bitmap │  inode table │      data blocks        │
└──────────┴──────────────┴─────────────┴──────────────┴─────────────────────────┘
   地图         谁空着          谁空着        文件身份证          真正的字节
  的地图      (inode)         (data)          数组
```

- **superblock（第 0 块）**——「地图的地图」。记录上面每一段从哪块开始、有多少块、总共几个 inode、根在哪。**它自描述**：读盘先读它，其他一切位置都从它算出来，代码里不写死。
- **inode bitmap / data bitmap**——两张「占用表」，每 1 bit 代表一个对象空闲还是被占。
- **inode table**——所有文件的「身份证」排成的数组。
- **data blocks**——文件内容真正躺的地方。整盘绝大部分是这一段。

### 每段填的是什么 —— 盘上其实只有三个结构

把每个区和「填充它的东西」对上：

| 区 | 里面是什么 |
|---|---|
| superblock（第 0 块）| 一个 `SuperBlock` |
| inode bitmap | 裸 bit，第 `k` 位 = 第 `k` 号 inode 占没占 |
| data bitmap | 裸 bit，第 `i` 位 = 第 `data_start + i` 块占没占 |
| inode table | `DiskInode` 数组，每块 4 个 |
| data blocks | 普通文件是裸字节；目录是 `DirEntry` 数组，每块 16 个 |

bitmap 是纯 bit、普通文件的数据块是纯字节，所以**真正的「结构体」只有三个**。三个都 `#[repr(C)]`、无 padding、字段是定宽小端 `u32`（换句话说：盘上的字节能原样映射成这些结构，跨机器一致）：

```rust
// 占第 0 块。「地图的地图」：每个区从哪开始、多长，全记在这。读盘第一件事就是读它。
struct SuperBlock {
    magic: u32,               // "RFS1"，认盘用
    block_size: u32,          // 512
    total_blocks: u32,        // 整盘块数
    ninodes: u32,             // inode 总数（格式化时定死）
    inode_bitmap_start: u32,  inode_bitmap_len: u32,   // ┐
    data_bitmap_start:  u32,  data_bitmap_len:  u32,   // │ 四个区各自的
    inode_table_start:  u32,  inode_table_len:  u32,   // │ (起始块, 块数)
    data_start:         u32,  data_len:         u32,   // ┘
    root_inode: u32,          // 树的入口，固定为 0
}

// 填满 inode table，每块 4 个（512/128）。这就是「文件本体」——注意它没有名字。
struct DiskInode {
    type_: u32,               // 0=Free 1=File 2=Dir（存原始 u32，读到坏块不会 UB 成非法枚举）
    size: u32,                // 文件真实字节数（读取按它截断，跟分配了几块无关）
    nlink: u32,               // 几个名字指着我；归零才真正回收
    _reserved: u32,           // 占位凑满 128B，留给以后的 mode/uid/时间戳
    direct: [u32; 26],        // 逻辑块 0..=25 → 物理块号（0 表示「没有这一块」）
    indirect: u32,            // → 一个装 128 个块号的间接块
    double_indirect: u32,     // → 一个装 128 个「间接块号」的块
}

// 填满目录的 data block，每块 16 个（512/32）。一个目录 = 一串这个。
struct DirEntry {
    inode: u32,               // 指向哪个 inode —— 这就是「名字 → inode」的那根指针
    name_len: u8,             // 名字占了 name 的前几字节
    name: [u8; 27],           // 不是 NUL 结尾：长度另存，27 字节全部可用
}
```

`name` 不用 NUL 结尾，而是显式存长度：取长度 O(1)（不必扫终止符）、27 字节一个不浪费、名字里能出现任意字节。代价是 `name_len` 是盘上的裸 `u8`，读回来必须先夹到 `27` —— 与 `type_` 存原始 `u32` 同一条理由：**坏盘上的字节不能让代码越界或 UB。**

一眼能看出三件事：

- **`SuperBlock` 只存位置信息**，一个文件字节都不装——它是「区的目录」（区域的目录，不是文件目录）。
- **`DiskInode` 里根本没有 `name` 字段**——这就是 §3 那一跳的物证：名字不在文件本体里，在 `DirEntry` 里。
- **`DirEntry` 小到只有「指针 + 名字」**——目录之所以能当成普通文件对待，正因为它的内容不过是这种小记录的数组。

一个贯穿全文的区分：

| | 元数据 (metadata) | 数据 (data) |
|---|---|---|
| 是什么 | 描述「东西在哪、多大、是什么」 | 东西本身的字节 |
| 在哪 | super / bitmap / inode table | data blocks |
| 例子 | 「文件 f 有 3KiB，数据在第 900、901、1200 块」 | 那 3KiB 的实际内容 |

文件系统的活儿，说到底只有两种：**改元数据** 和 **搬数据字节**。

## 3. 最重要的一跳：文件 ≠ 名字，文件 = inode

这是整个 Unix 式文件系统设计的**核心认知**，没绕过去的话后面全是浆糊。

**一个文件不是它的名字。一个文件是一个 inode。**

- **inode** 是文件的本体：它记录 `类型`（普通文件/目录）、`大小`、`硬链接数`，以及**数据块在哪**（见 §4）。inode 里**没有名字**。
- **名字**只是「指向某个 inode 的指针」，存在**目录**里（见 §5）。

一旦接受「名字和文件是分开的」，很多东西立刻自洽：

- 一个文件可以有**多个名字**（硬链接）——多条目录项指向同一个 inode。
- **改名**根本不碰文件本体——只动目录里那条指针。
- **删名字 ≠ 删文件**——所以 inode 要记 `nlink`（有几个名字指着我）。删到 `nlink==0` 才真正回收这个文件。

### inode 按「号」寻址，不靠搜索

inode table 是个**数组**，inode 有编号（inode number）。第 `k` 号 inode 的位置是**算出来的**，不是搜出来的：

```
第 k 号 inode 在  第 (inode_table_start + k / 4) 块  的第 (k % 4) 个槽
                                        ↑ 每块塞 4 个 inode（512 / 128）
```

给你一个 inode 号，一次块读就拿到它。**O(1)，无需扫盘。** 这就是为什么 Unix 文件系统里，「拿到 inode 号」几乎等于「拿到了文件」。

## 4. inode 怎么把「第 N 个字节」定位到「哪个块」

一个文件的内容，字节是**散落在任意数据块**里的——第 0 块可能在物理第 900 块，第 1 块可能在第 1200 块，不要求连续。那怎么知道「文件的第 N 个字节」在哪？

**inode 里存着一张「逻辑块号 → 物理块号」的映射表**，叫 block map。读文件第 `off` 字节：

```
逻辑块号 lbn = off / 512        （文件的第几块）
块内偏移      = off % 512        （在那块里的第几字节）
物理块号      = block_map(lbn)   ← 查 inode
```

问题是 block map 不能全用一张平表存——小文件不该为此浪费空间，大文件又得存得下。经典解法是**分级指针**：

```
        inode
        ┌─────────────────────────────┐
        │ type / size / nlink         │
        │                             │
        │ direct[0]  ──────────────►  data block   ┐
        │ direct[1]  ──────────────►  data block   │ 前 26 块
        │   ...                       ...          │ 直接命中
        │ direct[25] ──────────────►  data block   ┘
        │                             │
        │ indirect   ───►  [ptr,ptr,...,ptr]         接下来 128 块
        │                    128 个    └──► data      （一次间接）
        │                             │
        │ double_indirect ─►[ptr,...]                再往后 128×128 块
        │                    └─►[ptr,...]            （两次间接）
        │                         └──► data          │
        └─────────────────────────────┘
```

心智模型：**越靠前的块越便宜。** 小文件全落在 direct，读 inode 就知道块在哪；文件长大了才动用间接块（间接块本身也是从 data 区分配的一个普通块，里面塞满 4 字节的物理块号）。

我们的具体容量：

| 区段 | 覆盖逻辑块 | 累计文件大小 |
|---|---|---|
| 26 个直接指针 | 0 .. 25 | ≤ 13 KiB |
| 1 个单间接（128 指针）| 26 .. 153 | ≤ 77 KiB |
| 1 个双间接（128×128）| 154 .. 16537 | ≤ **~8.07 MiB** |

两条约定：

- **指针为 `0` 表示「没有这一块」。** 因为第 0 块是 superblock，永远不可能是某个文件的数据块，`0` 就能安全地当「空」哨兵。
- 文件的**真实长度看 inode 的 `size`**，不看分配了几块。size 之外的部分即使块里有旧字节也不算数（读取按 size 截断）。

## 5. 目录：内容是「名字 → inode」列表的文件

**目录不是什么特殊的魔法结构。目录就是一个文件**——只不过它的内容被解释成一串**目录项 (DirEntry)**，每项是一对：

```
( inode 号 , 名字 )      ← 32 字节一条，一块塞 16 条
```

就这样。「目录里有文件 hello.txt，它是 7 号 inode」这句话，在盘上就是目录这个文件的内容里有一条 `(7, "hello.txt")`。

这一跳带来的自洽：

- **树是递归、统一的。** 目录里能装目录，因为目录也只是文件；子目录就是「某条目录项指向的、类型为 Dir 的 inode」。
- 一个目录的**大小**、它的内容**放在哪些数据块**，全走 §4 那套 inode 机制，和普通文件**一模一样**。目录唯一的不同只是「内容被当成 DirEntry 数组解读」。
- **根目录**是编号**固定**的 inode（0 号）。它是整棵树递归的**锚点**——你得有个不靠名字就能找到的入口，否则「按名字找」永远没有起点。

### 删条目：压实，不留空洞

删中间一条时有两种做法，我们选后者：

| | 置空标记（tombstone） | **末位交换 + 缩容（本项目）** |
|---|---|---|
| 删第 k 条 | 把第 k 槽标记成空 | 把**最后一条搬到第 k 槽**，再把目录缩短 32 字节 |
| 需要哨兵值 | 要（得留一个「空」的表示法） | **不要** |
| 读目录 | 每个 reader 都得跳过空槽 | `size/32` 条**全部有效**，无脑遍历 |
| 判空 | 得扫一遍 | **`size == 0`，O(1)** |
| 目录大小 | 只增不减；反复增删会一直膨胀 | 跟着条目数缩，空出整块就还给 data bitmap |
| 代价 | —— | **不保序** |

不保序不是问题：`readdir` 本来就不承诺顺序。**对照页表**——页表项的**下标就是地址**，所以有语义、不能搬动去补空洞；目录项的下标不携带任何含义，因此可以压实。这一条差异正是「目录是数组」和「页表是数组」的分水岭。

## 6. 路径解析：沿着树一层层走

有了 §3（名字→inode）和 §5（目录是名字表），「按路径找文件」就是纯机械的重复动作。找 `/notes/todo.txt`：

```
1. 从 ROOT_INODE(0) 拿到根 inode        ← 唯一的固定入口
2. 把它当目录读，在条目里找 "notes"     → 得到 inode 号，比如 9
3. 读 9 号 inode，把它当目录读，找 "todo.txt" → 得到 inode 号，比如 12
4. 12 号 inode 就是目标文件
```

心智模型：**路径里每一个 `/` 分隔的名字，对应一次「读一个目录 + 在里面查名字」。** 这解释了为什么深路径更慢（层数 × 每层的目录读），也解释了为什么「拿到 inode 号」之后的读写就跟路径无关了——路径只在**定位**阶段用一次。

---

## 7. 分配：一切都是翻一个 bit

「哪些 inode 空着、哪些数据块空着」用两张 **bitmap** 记：**1 bit 管 1 个对象，`0` = 空闲，`1` = 占用**。

- **分配** = 找到第一个 `0` 位，置 `1`，返回它的下标。
- **释放** = 把对应位置回 `0`。

为什么用 bitmap 而不是空闲链表：紧凑（65536 块的占用状态才 8KiB），扫描找空位简单，而且**能 O(1) 回答「某个具体的块占没占」**（链表做不到）。

一个容易错的点——**下标和块号不是一回事**：

- inode bitmap 第 `k` 位 ↔ 第 `k` 号 inode。
- data bitmap 第 `i` 位 ↔ 物理第 `data_start + i` 块。**位图管的是数据区，不是整盘**；第 0 位是数据区的第一块，不是盘的第 0 块。

## 8. 增删改：把前面拼起来

到这里，所有操作都只是 §3–§7 的组合。没有新机制。

**建文件 `/d/f`：**
1. 翻 inode bitmap 拿一个空 inode，初始化成「普通文件、size=0、nlink=1」。
2. 解析到目录 `d` 的 inode（§6），在它的内容里加一条目录项 `(新inode号, "f")`（这可能需要给 `d` 这个「文件」再分配一个数据块——§4）。

**写数据：**
- 按需从 data bitmap 分配数据块，把物理块号填进 inode 的 block map（必要时先分配间接块），拷字节进去，更新 `size`。

**读数据：**
- 按 `size` 截断，逐个逻辑块用 block map 查到物理块，拷出字节。

**改长度（`set_len`）：**
- 变长的**唯一逆操作**，写入时的隐式增长走的是同一套 block map。缩短：把整块落在新末尾之外的数据块全部还给 data bitmap，空掉的间接块本身也还掉；最后**把还留着的那一块里超出新长度的字节清零**——因为全层都依赖一条不变量：**`size` 之外、块内的字节永远是 0**，否则以后再变长会把删掉的旧内容读回来。变长：只挪 `size`，新范围是个洞，读作 0，写到才分配。
- `set_len(0)` 就是「释放全部数据块」，所以删 inode 复用它，不另写一份。

**建硬链接：**
- 目标 inode 的 `nlink++`，再往目录里加一条指向它的目录项。**先加计数、后挂名字**（理由见 §10）。目录不许硬链接：没有 `..` 可回溯，成环了没人能发现、也解不开。

**删文件：**
- 从父目录里**压实掉**那条目录项（末位搬过来、目录缩 32 字节，见 §5）→ inode 的 `nlink--` → 如果归零，释放它所有数据块（data bitmap 翻回 0）并释放 inode（inode bitmap 翻回 0）。
- 删目录前先查空（`size == 0`），非空拒绝。

全程你会发现，动作永远只有那两种：**改元数据（翻 bit、改 inode、改目录项）** 和 **搬字节**。

## 9. Cache：什么时候才真的落盘

磁盘慢。所以热块留在内存里，读写先打内存副本。我们用 **write-back（回写）**：

- 改一个块 = 改内存里的副本，给它打上 **dirty** 标记。**不立即写盘。**
- dirty 块在**被挤出缓存**、或**显式 `sync()`**、或缓存 **drop** 时才真正写回磁盘。

心智模型：**在 `sync()` 之前，内存里的 cache 才是「真相」，磁盘是滞后的旧版本。** 推论——**忘了 sync，数据就没上盘**。这是 write-back 的代价，换来的是把多次改同一块合并成一次写。（对照 write-through：每次改都立刻写盘，永远一致但慢；我们不用它，因为想让你建立起 dirty/flush 这个正经概念。）

## 10. 崩溃一致性：我们做到哪

**我们不做 journaling。** 但写入**顺序**仍然是有模型的：**先写数据块，再写指向它的元数据。**

- 这样即使中途崩溃，最坏结果是**块被 bitmap 标了占用、却没有任何 inode 指向它**——「泄漏」。空间少一点，但没有任何文件指向垃圾数据。泄漏可容忍、日后可用 fsck 式扫描回收。
- 反过来的顺序（先改元数据、后写数据）崩溃会得到「指向垃圾内容的有效文件」——**那才是真正的损坏**。所以顺序不能反。

明确边界：**这不是生产级崩溃安全。** 它是教学 FS，假设单机、正常卸载（会 sync）。掉电一致性不是本项目当前目标。

---

## 11. 这个 FS 明确不做什么（划清边界）

不写清楚会一直有人问，所以列在这：

- **无权限 / 属主 / 时间戳。** inode 里留了一个 `_reserved` 字段，以后加 mode/uid/mtime 的时候用；现在没有。
- **无 journaling、无软链接（symlink）、无稀疏文件的特殊优化。**
- **固定上限**（格式化时或格式本身定死）：文件名 ≤ 27 字节，单文件 ≤ ~8 MiB，inode 总数在 `mkfs` 时定死。
- **目录项线性扫描**：在目录里找名字是从头扫到尾。小目录无所谓，大目录慢——我们不做 hash 目录 / B 树。
- **暂不涉及进程 / 文件描述符 / `open` 系统调用。** 本阶段 FS 由**内核代码直接驱动**验证（见项目里的 Phase 划分）。

这些不是「做不到」，是**故意不做**，为了先把上面 §1–§10 那套核心模型立起来、且能被 host 单测证明正确。加功能是以后的事。

## 12. 端到端走两遍（把模型钉死）

**例 A — 读 `/hello.txt`（假设它是 7 号 inode，3 KiB）：**

```
读 superblock                        → 知道各区起始块
从 ROOT_INODE(0) 读根 inode          → 摸 inode table 里根那一块
把根当目录读它的数据块               → 摸根的数据块，扫到 (7, "hello.txt")
读 7 号 inode                        → 摸 inode table 里第 7/4=1 块的第 3 槽
3KiB = 6 个逻辑块，全在 direct[0..6] → block map 直接给出 6 个物理块号
逐块读这 6 个 data block，拷 3KiB 出来  → 按 size=3072 截断
```

**例 B — 在 `/notes` 下建 `todo.txt` 并写 3 KiB：**

```
解析 /notes 到它的 inode（§6）
翻 inode bitmap → 拿到空号，比如 12；初始化 12 号为 File, size=0, nlink=1
往 notes 的目录内容里加一条 (12, "todo.txt")
                    （notes 这个"文件"若当前块满了，可能触发给它分配新数据块）
写 3KiB：翻 data bitmap 拿 6 个空数据块，块号填进 12 号 inode 的 direct[0..6]，
        拷字节，置 size=3072
sync()  → 所有被打脏的块（bitmaps、两个 inode、notes 的目录块、6 个数据块）此刻才落盘
```

两遍下来，如果你能说清「每一步摸了哪个区的哪块、改的是元数据还是数据」，这套心智模型就装进脑子了。
